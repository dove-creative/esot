# 저장 구조와 복구

[English](Architecture.md) · [프로젝트 개요](README.ko.md)

## 커밋과 파일 내용

| 위치 | 보관하는 정보 | 용도 |
| --- | --- | --- |
| 각 워크트리의 일반 파일 | 편집기가 읽고 쓰는 현재 내용 | 커밋 전 변경을 포함한 작업본이다. |
| 각 워크트리의 `.worktree/worktree.json` | 워크트리 이름, 공유 저장소 경로 | 현재 폴더에서 자신의 브랜치와 공유 이력을 찾는다. |
| 각 워크트리의 `.worktree/storage` | SHA-256 값으로 식별하는 파일 전체의 사본 | 같은 워크트리에서 내용이 같은 파일은 한 사본을 공유한다. |
| 로컬 공유 Git 저장소 | 커밋별 `files.json`(상대 경로와 해시), 부모 커밋, 워크트리별 브랜치 | 실제 리소스가 정리된 후에도 이력과 공통 조상을 조회할 수 있다. |

공유 저장소에는 워크트리의 실제 경로와 보관 한도, 공통 제외 규칙도 있다. `ESOT_HOME`은 초기화할 때 저장소의 상위 위치를 정한다. 복구 가능한 백업에는 공유 저장소와 보관하려는 리소스 사본이 모두 필요하다.

## 작업 파일 검사

각 워크트리는 파일 경로·크기·UTC 수정 시각·SHA-256을 `.worktree/scan-v1.json`에 캐시한다. 상태 확인과 커밋에서는 안정된 항목을 재사용하고 새 파일이나 변경된 파일의 해시를 계산한다. 계산한 키가 등록된 저장소에 이미 있으면 작업 파일과 보관 사본의 바이트를 비교한다. 같은 키로 다른 내용이 확인되면 작업을 중단하고 두 파일을 보존한다. 이 오류는 해시 충돌 또는 보관 사본의 손상을 나타낼 수 있다.

파일 수정 시각이 검사 시작 전 2초 이내이거나 미래이면 이후 검사에서 시각이 안정된 것을 확인할 때까지 다시 읽는다. ESOT가 복원이나 복구로 파일을 쓸 때는 해당 항목을 먼저 무효화한다. 외부 도구가 파일 크기와 과거 수정 시각을 그대로 유지하며 내용을 바꾸면 빠른 검사에서 놓칠 수 있다. 검사 캐시를 제거하면 다음 검사에서 전체 파일을 다시 확인한다. 기존 워크트리는 첫 검사에서 캐시를 생성한다.

## 보관과 복원

커밋 시점의 파일 전체를 보관하므로 편집기가 작업 파일을 덮어쓴 후에도 이전 버전을 식별할 수 있다. 보관 한도는 각 워크트리에서 현재 커밋이 참조하지 않는 사본의 바이트 합계에 적용된다. Common에 10GB, Unity에 0을 지정하면 Unity는 현재 커밋에 필요한 사본을 유지하고, 오래된 사본은 Common에 이미 보관된 범위에서 복원할 수 있다. 한도를 넘기면 먼저 과거 버전이 된 내용부터 정리한다.

`restore --source <commit> <path>`는 커밋에서 해시를 찾고, 등록된 워크트리에서 해당 사본을 읽어 작업 파일에 복원한다. 브랜치는 현재 커밋을 유지한다. 모든 사본이 정리된 경우 원본 내용을 복원할 수 없다.

## 충돌과 중단 복구

내용 충돌은 공통 조상·대상·보낸 쪽의 해시를 경로별로 비교하는 단계에서 판정한다. 경로의 부재도 하나의 상태이므로 삭제와 수정이 충돌할 수 있다. 현재 구현은 공통 조상 커밋을 하나로 정할 수 있을 때 병합한다.

파일을 반영하기 전에 ESOT는 참여 워크트리의 이전 커밋과 다음 커밋을 공유 저장소의 저널에 기록한다. 파일 반영이 끝나면 Git 브랜치들을 한 트랜잭션으로 갱신한다. 중단 뒤 `recover`는 적용할 경로마다 디스크 내용이 이전 값 또는 예정된 값과 일치하는지 확인하고 남은 작업을 이어간다. 둘과 다른 외부 편집을 발견하면 경로를 보고하고 저널을 보존한다.
